# 任务分类与出题规范

本基准包含三类任务。所有任务都必须满足 [通用要求](#通用要求)，并按各自分类补充要求出题。

## 通用要求

1. **真实性**：基于真实鸿蒙应用工程场景。
2. **可验证**：存在确定性的自动化验证；不允许全部依赖 llm as judge。
3. **参考解验证**：依靠专家是可以真实的做出来的，自动化验证后，奖励必须为 1。
4. **NOP 验证**：未做任何修改的初始环境运行测试，自动化验证后，奖励必须为 0。
5. **说明自洽**：`instruction.md` 只描述“要做什么”和必要约束，不泄露解法；测试只验证说明中提到或可合理推断的行为。
6. **环境一致**：遵循 [基准环境约定](environment.md)（HarmonyOS 6.1.1(24) / API 24、Pura 90 Pro 1256 × 2760、Asia/Shanghai、zh-Hans-CN、Harbor 0.24.0）。

## 1. Feature —— 基于工程项目做功能的实现

**场景**：给定一个初始的鸿蒙工程，要求 Agent 增加一个新功能。

- 环境：`/workspace/app` 为上游工程固定 commit 的快照。
- 说明：用产品需求语言描述功能，必要时给出 UI/接口约束（如组件 id、方法签名），以便测试定位。
- 测试：
  - 工程能编译通过；
  - 隐藏单元测试或 UI 测试覆盖新功能的核心行为；
  - 原有测试不回归。

## 2. Bugfix —— 缺陷修复

**场景**：给定存在缺陷的鸿蒙工程与一份缺陷的描述，要求 Agent 修复存在的问题。

- 环境：上游工程处于修复前状态，且真实存在这一类问题
- 说明：以 Issue 的形式描述现象、复现步骤、期望行为，**不指出出错位置**。
- 测试要求：
  - **Fail-to-Pass (F2P)**：修复前失败、修复后通过的测试；
  - **Pass-to-Pass (P2P)**：修复前后都应通过的回归测试，不影响现有功能的测试。
  - 奖励 = F2P 与 P2P 全部通过时为 1，否则为 0（可在 `reward.json` 中额外记录细分结果）。

## 3. Spec —— 规格驱动开发

**场景**：给定一份规格文档，要求 Agent 依据需求规格文档实现功能。

- 环境：
  - `/workspace/spec/`：spec 文档（Markdown，可附接口定义、数据模型、交互流程、截图等）；
  - `/workspace/app`：鸿蒙工程脚手架或已有工程。
- 说明：`instruction.md` 指向 spec 文档，并说明交付范围；spec 本身是需求的唯一事实来源。
- 测试：根据 spec 中的验收标准（Acceptance Criteria）逐条编写，可使用 `reward.json` 按条目给出部分得分。
- 要求：spec 中每一条被测试的行为都必须有明确描述；避免测试 spec 未规定的实现细节。

## 环境内路径约定

| 路径 | 含义 |
| --- | --- |
| `/workspace/app` | 鸿蒙工程根目录（Agent 的主要工作目录） |
| `/workspace/spec` | Spec 任务的规格文档 |
| `/tests` | 验证阶段由 Harbor 挂载的测试文件（Agent 不可见） |
| `/logs/verifier/reward.txt` / `reward.json` | 奖励输出 |
